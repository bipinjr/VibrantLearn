# TESTING.md — what we test and why

A test exists to stop a specific bad thing reaching a student the night before their exam. If you cannot name the bad thing, do not write the test.

---

## 1. The pyramid, and what sits where

| Layer | Tool | Count today | What it protects |
|---|---|---|---|
| Unit (web) | Vitest | ~135 | Parser, scheduler, formatters, username rules, redirect guard |
| Component | Vitest + Testing Library | small | Quiz behaviour, keyboard interaction |
| Unit / integration (API) | pytest | 33 + 5 needing a database | Auth, validation, rate limits, profile, waitlist |
| Database | pgTAP | 38 | **Row Level Security** — the claim the whole product rests on |
| End to end | Playwright (`apps/web/e2e/smoke.py`) | 18 steps | The demo script works start to finish |
| Manual | a human | checklist | Language quality, how it feels, exam-night realism |

Fast tests run on every commit. The database and e2e suites run in CI and before any release.

## 2. Non-negotiable tests

These are the ones that may never be deleted or skipped.

### 2.1 One student cannot see another's data

`supabase/tests/rls.test.sql`. Two users, a full set of rows each, then every cross-user read and write is asserted to fail. **Every new table adds an assertion here before it ships.** Without this suite, "your notes are private" is a hope, not a fact.

### 2.2 A plan always contains real topics

`lib/demo/scheduler.test.ts` → `expectRealTopics()`.

A crash plan once came back with no syllabus topics at all when a student opened the app at 10:40 PM; the exam-day morning only ever held fixed revision items. Every scheduler test started at 8:30 PM, so nothing caught it. The regression test now starts at 10:40 PM and asserts the plan teaches something.

**Rule learned: test the hour a student actually panics, not the convenient hour.**

### 2.3 The redirect guard

`lib/safe-next.test.ts`. Browsers strip control characters before resolving a URL, so `/<tab>/evil.com` becomes `//evil.com`. The suite covers tabs, newlines, nulls, C1 characters, and the `/..//evil.com` normalisation case — the last one was found by the test after the first fix looked right.

### 2.4 Uploads refuse hostile files

Fixtures live beside the e2e tests (gitignored, regenerated by the test):

| Fixture | Must |
|---|---|
| `evil.exe` renamed `notes.pdf` | be rejected on magic bytes, not extension |
| a zip bomb `.docx` | be rejected on the uncompressed-size ratio |
| an XXE `.xml` | parse with entities disabled, no outbound request |
| a 49 MB PDF | process successfully |
| a 51 MB PDF | be refused with the split-it message |
| a PDF containing "ignore all previous instructions…" | change nothing about the answer |

### 2.5 The AI never ships unvalidated output

Every LLM response is parsed into a schema before a student sees it. Tests cover: valid output, malformed JSON (one repair retry), still-malformed output (graceful fallback), empty response, timeout, and 429.

## 3. How to write a test here

- **Name the failure, not the function.** `crash: late at night, still teaches real topics` beats `buildPlan works`.
- **Use real content.** Java and DBMS topics from the seed, Kanglish and Hinglish phrasings students actually type. No `foo`/`bar`.
- **Fix the clock.** Anything touching deadlines passes an explicit `now`. Asia/Kolkata, always — a test that passes only before 6 PM is worse than no test.
- **Table-driven for parsers.** `it.each` with one row per phrasing; the parser suite is the cheapest place to add a language case.
- **Assert the user-visible outcome**, not the internals. "The plan contains a topic" survives a refactor; "the loop ran four times" does not.
- **One behaviour per test.** When it fails, the name should tell you what broke.

## 4. Coverage expectations

Not a percentage. These specific things must be covered:

- [ ] Every API endpoint: happy path, unauthenticated, **cross-user**, over-limit, malformed body
- [ ] Every table: owner can, non-owner cannot (pgTAP)
- [ ] Every parser intent, in English, Kanglish, Hinglish and native script
- [ ] Every plan mode: sprint, crash, steady, deep — including the edge hours
- [ ] Every upload rejection path
- [ ] Every LLM failure path
- [ ] Every screen: loading, empty, error, and success states
- [ ] Reduced motion: every animation has a tested fallback

Target ≥ 40 parser phrasings (PRD F5) and ≥ 20 scheduler/parity cases once the Python port lands.

## 5. Running everything

```bash
# fast — run before every commit
cd apps/web && pnpm lint && pnpm typecheck && pnpm test
cd apps/api && uv run ruff check . && uv run mypy app && uv run pytest -q

# database — after any migration
npx supabase db push --linked
npx supabase test db --linked                      # expect 38/38
npx supabase db advisors --linked --fail-on error  # expect clean

# end to end — before any release
START-DEMO.bat
uv run --no-project --with playwright python apps/web/e2e/smoke.py   # "All 18 steps passed."
EXPECT_AI=1 uv run --no-project --with playwright python apps/web/e2e/smoke.py  # with a Groq key

# production build
cd apps/web && pnpm build
```

CI runs the fast suites, gitleaks, `pnpm audit --prod`, `pip-audit`, and the database suite on every pull request. A red pipeline is never merged.

## 6. Manual checks a machine cannot do

Before any demo or release:

- [ ] **Language quality** — a fluent Kannada speaker and a fluent Hindi speaker read the interface and one set of notes. Does it sound like a person or like a translation? Are technical terms still in English?
- [ ] **Exam-night realism** — open the app at 10:30 PM with a 10 AM exam. Is the plan something a real student would follow?
- [ ] **Phone, one hand** — 360 px, thumb only. Can you reach everything? Is anything hidden behind the composer or the bottom bar?
- [ ] **Slow network** — DevTools 4G throttle. Does anything jump, flash or feel broken?
- [ ] **Two devices, one account** — sign in on a laptop and a phone; the same sessions appear.
- [ ] **The cover-the-logo test** — hide the wordmark. Could this be any other AI startup's page? If yes, the design is not done ([FRONTEND.md](FRONTEND.md) §1).

## 7. When a bug is found

1. Write a failing test that reproduces it, with the real inputs that caused it.
2. Fix it.
3. Keep the test, named after the failure.
4. Ask why no existing test caught it, and fix that gap too — that is usually the more valuable change.
5. Add a line to `MEMORY.md` → *Session log*, and to the *Security review log* if it was a security bug.
